# 一人指挥多角色 Agent · 系统设计

> 本文回答一件事：一个人怎么通过一个对话框，指挥一支有分工、有记录、有验收标准的 Agent 团队，把「餐饮经营分析系统 · 收入分析 Demo」做出来并留痕。
>
> 本文是**生产方式**的设计，不是产品架构。产品架构见 `openspec/changes/build-catering-analysis-platform/design.md`。

---

## 1. 一句话

用户只面对一个对话框（Web 会话，或后续接入的飞书/微信），背后是一支按角色分工的 Agent 团队；
每个角色只拿自己需要的上下文，所有产出落在 OpenSpec，所有代码落在 GitHub。

本期（一周 Demo）先跑通「Web 会话 + DSH Agent Teams + OpenSpec + GitHub」四件套；
飞书/微信入口按本文第 6 节预留，作为演示故事与下一阶段能力，不在本周强行接通。

---

## 2. 六层结构

```
┌──────────────────────────────────────────────────────────────┐
│ L1 入口层    Web 会话（本期）/ 飞书 · 微信机器人（后续）        │
│              用户只说人话：要什么、什么时候要、什么算做完       │
├──────────────────────────────────────────────────────────────┤
│ L2 指挥层    Team Lead（主会话）                               │
│              拆需求 · 定优先级 · 分派 · 验收 · 合并 · 汇报      │
├──────────────────────────────────────────────────────────────┤
│ L3 角色层    PM / 架构师 / 数据工程师 / 前端工程师 / 评审官 / 文档 │
│              每个角色一个独立上下文，只拿任务书+规格+代码路径    │
├──────────────────────────────────────────────────────────────┤
│ L4 执行层    Worktree Space（一任务一空间，可并行）             │
│              遇到跨文件并行改动时启用；串行小任务可直接在主仓做  │
├──────────────────────────────────────────────────────────────┤
│ L5 记录层    OpenSpec（proposal → specs → design → tasks → archive）│
│              需求、方案、任务、验收标准、变更原因全部留痕        │
├──────────────────────────────────────────────────────────────┤
│ L6 存储层    GitHub（origin + target 双远程）                   │
│              代码、文档、规格同仓，可回溯、可协作               │
└──────────────────────────────────────────────────────────────┘
```

## 3. 一次需求的完整旅程（本期实际走法）

```
用户（Web 会话）：「收入分析要能下钻到门店，看是客流还是客单的问题」
   │
   ▼
Lead：判断需求类型
   ├─ 小改（文案、样式）      → 直接指派给对应工程师，不新开 change
   ├─ 新功能 / 新模块        → 走 OpenSpec change
   └─ 修 bug                 → 对应工程师修 + 补测试
   │
   ▼（新功能）
PM：写 proposal（为什么 / 做什么 / 不做什么）→ 更新 specs 场景
   │
   ▼
Lead：把 proposal 摘要给用户 → 用户回「可以」
   │
   ▼
架构师：写 design（数据模型 / 接口契约 / 页面结构）→ 拆 tasks（可并行、可验收）
   │
   ▼
Lead：建 Worktree Space（或串行分派），按角色派单
   ├─ 数据工程师 → 指标引擎 + 接口 + 单测 + 手算对照
   ├─ 前端工程师 → 页面 + 图表 + 下钻 + 空态
   └─ 两端共用 shared/fixtures 回归
   │
   ▼
评审官：逐条对 specs 场景、跑测试、核对 Excel 数字、提阻塞意见
   │
   ▼
Lead：合并 → 推 GitHub（origin + target 双推）→ 更新 tasks 勾选
   │
   ▼
用户（Web 会话）：收到「做完了，预览地址 / 演示动线 / 还差什么」
```

## 4. 为什么这样设计

| 问题 | 传统做法 | 这套做法 |
|---|---|---|
| 需求失忆 | 聊天记录里翻 | OpenSpec 里每个 change 有 proposal + specs，永久可查 |
| 一个 Agent 越做越乱 | 上下文全塞进一个会话 | 每个角色独立上下文，只拿自己需要的 |
| 并行互相踩 | 串行等 / 同一文件冲突 | Worktree Space 一任务一空间；同文件范围只给一个 owner |
| 质量靠感觉 | 没有验收标准 | specs 写死场景与数字，评审官逐条对 |
| 代码丢失 | 本地副本 | GitHub 单一真相，双远程备份 |
| 用户看不懂 | 日志、diff | 只在需要拍板时问；汇报说人话 |

## 5. 角色、写入范围与闸门

角色定义见 `docs/agents/roles.md`。三条铁律：

1. **一个任务一个 owner**，同一文件范围不允许两个 Agent 同时写。
2. **上游没确认，下游不动手**：proposal 没批准，架构师不写 design；design 没定，工程师不写代码。
3. **结论回 Lead，不横向私聊**：避免上下文漂移。

合并闸门（每次合并前必须全绿）：

- `openspec validate build-catering-analysis-platform --strict` 通过；
- 后端 `pytest`、前端 `npm test`、`npm run build` 通过；
- 评审官没有阻塞意见；
- 关键数字与 Excel 示例一致（验收清单见 tasks）。

> 全局硬规则：**所有 SDD 类开发，代码实现前必须由用户审批文档**（CLAUDE.md 已约定）。本仓库当前 change 的 proposal / specs / design / tasks 需要用户点头后才可开工。

## 6. 入口层：为什么本期先用 Web 会话

| 入口 | 能力 | 本期取舍 |
|---|---|---|
| Web 会话（DSH） | 同一个对话框；直接看文档、看 diff、审批 | **本期主入口**，不增加配置成本 |
| 飞书（dsh-im） | 群内 @ 机器人下需求；任务过程卡/实时直播；结果文件回传；可绑定工作区 | 写进演示脚本与设计；本周不实际接入 |
| 微信（dsh-im） | 私聊/群聊机器人；分段文本回复 | 同上 |
| GitHub Issue | 用 issue 描述需求，Agent 认领并开 PR（dsh-superagent 模式） | 作为二期可选：三人以上协作时再启用 |

接入方式（下一阶段，配置项均已在本机 DSH 插件中可用）：

1. DSH「设置 → IM机器人」扫码创建飞书机器人；
2. 工作区指到本仓库，Agent Preset 用默认，模型 deepseek-flash；
3. 群聊「被 @ 时响应」，任务过程展示选「实时过程卡」（投屏演示友好）；
4. 用户侧只需 @ 机器人说需求，Lead 在同一会话里继续分派；审批可用「批准 / 拒绝」回复。

## 7. 执行层：什么时候用 Worktree Space

- **不用**：串行任务、单文件小改、跨文件但顺序明确（Lead 直接分派，主仓顺序写）。
- **用**：数据工程师与前端工程师同时动工、或两个独立模块并行、或需要「部署验收 + 合并闸门」时。
- 一任务一空间、一分支；合并前跑冒烟；冲突与未提交改动交回 agent 处理。

本期两人并行（数据 / 前端）是常态，D3 起建议启用 Worktree Space，避免 `backend/` 与 `frontend/` 之外的共享文件（`shared/fixtures`、`README`）互相覆盖。

---

## 8. 记录层：OpenSpec 怎么用

- 新功能：`openspec new change <id>` → proposal → specs → design → tasks → 用户审批 → 实现 → `openspec archive`。
- 已有 change：小改在 `changes/<id>/tasks.md` 追加一条并勾选，不新开 change。
- 需求变更：改 proposal 的「What Changes」并说明原因；已归档的规格通过新 change 修改。
- 每次合并后更新 tasks 勾选状态；演示前把「已完成 / 未完成 / 已知问题」写进 `docQA/` 的会话记录。

## 9. 存储层：双远程

```bash
git remote -v
# origin  https://github.com/cfmypian/CateringBusinessAnalysis-dshSA.git
# target  https://github.com/c4thmy/CateringBusinessAnalysis.git

git push origin main
git push target main
```

- `origin` 保留历史与实验记录；`target` 是面向演示与商用的主仓库。
- tag 规则见 README：每次里程碑打 `v0.x.0`，双远程都推。

## 10. 本期的边界

- 不接大模型：所有「AI 洞察」由规则函数生成，规则来源为 PPT 知识库页（67–79）与 Excel 阈值。
- 不做多租户、细粒度权限：单管理员登录。
- 不做第三方平台 API 自动拉数：先 Excel/CSV 导入。
- 飞书/微信只做设计文档与演示脚本，不本周接通。
- 毛利 / 费用 / 顾客 / 总结 / 沙盘：本期只做导航与页面骨架，业务逻辑二期。
